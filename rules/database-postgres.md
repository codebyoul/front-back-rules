# Database rules — PostgreSQL (a currently supported major version)

Read with `backend.md` §4 §6 §7, `security.md` §14, `performance.md` §3. Every rule is MUST unless marked SHOULD.
Pin the minimum major version in the project entry file; features below note the version that introduced them.

## 1. Engine and connection

- UTF-8 database encoding; a deliberate collation (prefer ICU or `C`/`en-US-x-icu` provider choices documented per project). **A collation/libc version change can silently corrupt text indexes: after an OS/libc/ICU upgrade run `REINDEX` on text indexes** (and monitor the collation-version warning).
- **UTC only (NON-NEGOTIABLE, `backend.md` §7):** `ALTER DATABASE … SET timezone TO 'UTC'` and session `TimeZone` = UTC on every connection; the DB never converts zones for business logic; the app writes UTC.
- **Timeouts are set, never default-infinite:** `statement_timeout` (per role/session; longer for batch roles), `lock_timeout` (short in migrations), `idle_in_transaction_session_timeout` (a forgotten open transaction blocks vacuum and locks).
- Auth `scram-sha-256`; `pg_hba.conf` restrictive (no `trust`); TLS with certificate verification (`sslmode=verify-full`); no public exposure.
- **Connection pooling is mandatory at scale** (each connection is a process): PgBouncer/pooler or built-in pool. In **transaction-pooling mode** there is no session state: no session-level `SET`, no session advisory locks, no `LISTEN/NOTIFY`, careful with prepared statements. Pool size ≈ cores × 2–4 for the primary workload, from measurement.

## 2. Types and schema

- **Time:** `timestamptz` always, read and written in UTC (never `timestamp` without time zone, never a local-zone session); calendar-only values `date`; durations `interval`.
- **Money:** `numeric(p,s)` + currency code; never `float`/`double precision`/`money`.
- **Text:** `text` + `CHECK (char_length(col) <= n)` (or `varchar(n)` when a hard limit is a domain fact); validate the same limit at the boundary.
- **Ids:** `bigint GENERATED ALWAYS AS IDENTITY` internal PK plus a public opaque `uuid`, or time-ordered UUIDv7 as PK (`uuidv7()` built in from PostgreSQL 18; otherwise generated by the app). **Random UUIDv4 as PK on large write-heavy tables hurts index locality — avoid.** Never expose sequential ids. Sequences have gaps.
- **Enums:** `text` + `CHECK`, a lookup table, or `CREATE TYPE … AS ENUM` (values can be added, not removed/reordered cheaply). Choose per how often values change.
- `boolean NOT NULL DEFAULT …`; `jsonb` only for genuinely schemaless payloads (index with GIN/expression indexes, validate with `CHECK`/app schema); never model relational data in JSON. Arrays sparingly.
- Case-insensitive uniqueness: `citext` or a unique index on `lower(col)`; decide deliberately.
- **NOT NULL by default**; explicit defaults. Generated columns (12+) for derived values.
- Range types + **exclusion constraints** (`EXCLUDE USING gist`) for "no overlapping bookings/periods".

## 3. Constraints and integrity

- Integrity lives in the database: `NOT NULL`, `UNIQUE`, `FOREIGN KEY`, `CHECK`, exclusion constraints. A concurrency loser hits a constraint and is mapped to 409/422 (SQLSTATE `23505` unique, `23503` FK, `23514` check, `23P01` exclusion).
- **Partial unique indexes** enforce conditional uniqueness natively: `CREATE UNIQUE INDEX … ON t (col) WHERE deleted_at IS NULL` (one live pairing per phone, one open run per item, unique among non-deleted). `UNIQUE … NULLS NOT DISTINCT` (15+) when NULLs must collide.
- FKs: `ON DELETE RESTRICT` by default; **no cascade delete** on business data; `DEFERRABLE INITIALLY DEFERRED` only when a real circular insert needs it.
- **Postgres does NOT index foreign keys automatically: index every FK column** (composite where queries filter on it).
- `INSERT … ON CONFLICT (cols) DO NOTHING | DO UPDATE` is the idempotent upsert; specify the conflict target explicitly; use `RETURNING` to avoid re-reading.
- **[multi-tenant]** `tenant_id` is the first column of composite indexes; unique constraints are per tenant; child FKs may include `tenant_id` to prevent cross-tenant links.

## 4. Row-Level Security (defense in depth) [multi-tenant]

- Enable RLS on tenant-owned tables: `ALTER TABLE t ENABLE ROW LEVEL SECURITY; ALTER TABLE t FORCE ROW LEVEL SECURITY;` with policies on `tenant_id = current_setting('app.tenant_id')::uuid`.
- The app connects as a **non-owner role without `BYPASSRLS`** (owners and superusers bypass RLS unless `FORCE`d; superusers always bypass). Set the tenant per transaction with `SET LOCAL` (safe with transaction pooling), never session-level `SET`.
- RLS is a second layer: application scoping and tests remain mandatory. Policies are indexed (`tenant_id` leading) and tested (a query without the setting returns nothing/fails, another tenant's row is invisible).
- `SECURITY DEFINER` functions set an explicit `search_path` and validate inputs.

## 5. Indexing

- Default **B-tree**; **GIN** for `jsonb`, arrays, full-text (`tsvector`), trigram (`pg_trgm`, for `LIKE '%x%'`/fuzzy); **GiST** for ranges/exclusion/geo; **BRIN** for huge append-only, time-correlated tables.
- **Composite order** = equality columns first, then range, then sort; **partial indexes** for hot subsets (`WHERE status='open'`); **expression indexes** for `lower(email)`; **covering** with `INCLUDE (…)` to enable index-only scans.
- Every index earns its place (proven by `EXPLAIN`); find unused ones with `pg_stat_user_indexes`; drop duplicates. Indexes cost writes and can block HOT updates.
- **Create/drop indexes with `CREATE INDEX CONCURRENTLY` / `DROP INDEX CONCURRENTLY`** on live tables (cannot run inside a transaction; a failed build leaves an INVALID index — check and drop it).
- Sorting/filtering columns for user-facing lists are indexed to match the keyset order.

## 6. Queries and pagination

- Parameterized queries only (`security.md` §4). Select only needed columns.
- **Keyset pagination** for large lists (`WHERE (created_at, id) < ($1,$2) ORDER BY created_at DESC, id DESC LIMIT n`); deep `OFFSET` is O(offset); always add a unique tie-breaker.
- `count(*)` on big tables is a scan: use keyset "has next", rollups, or `pg_class.reltuples` estimates for approximate totals.
- `EXPLAIN (ANALYZE, BUFFERS)` is attached to any change adding a hot query; watch for seq scans on large tables, row-estimate misses, sorts spilling to disk, nested loops on big sets.
- Prefer `EXISTS`/`NOT EXISTS` over `IN`/`NOT IN` with nullable subqueries (`NOT IN` + NULL returns no rows). CTEs are inlined by default since 12 (use `MATERIALIZED` deliberately).
- Full-text: `tsvector` + GIN; use `websearch_to_tsquery` for user input (does not raise on syntax); escape `LIKE` wildcards; cap term length.
- Avoid `SELECT *`, `ORDER BY random()`, per-row subqueries, N+1, and functions on indexed columns without a matching expression index.
- `LIMIT` without `ORDER BY` is nondeterministic — never in paginated code.

## 7. Transactions, isolation, locking

- Default isolation **READ COMMITTED**. Use `REPEATABLE READ`/`SERIALIZABLE` only where needed and **retry on serialization failure (`40001`) and deadlock (`40P01`)** a bounded number of times with jitter.
- Row locks: `SELECT … FOR UPDATE` (write intent), `FOR NO KEY UPDATE`, `SKIP LOCKED` (queue/claim patterns), `NOWAIT`; **advisory locks** (`pg_advisory_xact_lock`, transaction-scoped) for cross-row/cross-table mutual exclusion. Lock in a consistent order.
- Transactions are short: no external calls or user waits inside; always set `lock_timeout` for DDL/migration sessions.
- Optimistic concurrency `UPDATE … WHERE id=$1 AND version=$2` and check the affected row count.
- Long-running transactions and abandoned replication slots block vacuum and bloat tables: monitor and alert.

## 8. Migrations (zero-downtime)

- Forward-only once pushed; **expand → backfill → switch → contract**. **DDL is transactional in Postgres**: wrap migrations in a transaction so a failure leaves nothing half-done (except `CONCURRENTLY` operations).
- **Set `lock_timeout` (e.g. 3–5 s) and retry** in migrations: a DDL waiting behind a long transaction queues every later query behind it.
- Safe patterns: `ADD COLUMN` with a constant default is metadata-only (11+); add `NOT NULL` via `CHECK (col IS NOT NULL) NOT VALID` → `VALIDATE CONSTRAINT` → `SET NOT NULL` (12+ skips the scan); add FKs and CHECKs `NOT VALID` then `VALIDATE CONSTRAINT` (validation takes a weaker lock); create indexes `CONCURRENTLY`.
- Dangerous: column type changes and volatile defaults (table rewrite + `ACCESS EXCLUSIVE`), `ALTER TYPE … ADD VALUE` inside transactions (version limits), renames of live columns (use expand/contract), `VACUUM FULL`/`CLUSTER` on live tables.
- Backfills in chunks by key range, throttled, resumable, outside the request path; never drop/rename in the same release that stops using it.

## 9. Security

- **Roles:** an owner/migrator role (DDL) separate from the application role (DML on needed tables only); read-only role for reporting; no superuser for apps. `REVOKE ALL ON SCHEMA public FROM PUBLIC` and grant explicitly; default privileges configured.
- Column/row security for sensitive tables (RLS §4, column privileges); secrets encrypted by the app (or `pgcrypto` with keys outside the DB), never in plain columns; audit tables are append-only for the app role (no `UPDATE/DELETE` grant).
- Extensions are allow-listed and reviewed (`pgcrypto`, `pg_trgm`, `citext`, `btree_gist`, `pg_stat_statements` are common); managed-service availability checked.
- `log_statement`/`log_min_duration_statement` never expose bound secrets; `pg_stat_statements` normalizes literals.

## 10. Performance operations

- **Autovacuum is never disabled**; tune per hot table (`autovacuum_vacuum_scale_factor`, cost limits); watch dead tuples, table/index bloat, `n_dead_tup`, transaction-id age. Run `ANALYZE` after bulk loads.
- Enable `pg_stat_statements`; review top statements by total time and mean time; `auto_explain` for slow plans; log slow queries (`log_min_duration_statement`).
- Tune deliberately: `shared_buffers` (~25 % RAM), `effective_cache_size`, `work_mem` (per sort/hash node × connections — beware), `maintenance_work_mem`, `random_page_cost` for SSD, WAL/checkpoint settings; measure before and after.
- **Partitioning** (declarative) only for proven need — very large time-series or retention by dropping partitions; the partition key is part of unique keys.
- Read replicas lag: read-your-writes paths use the primary. Logical replication/CDC monitored for slot lag.
- Hot-row contention (counters) → sharded counters or rollup jobs, not a single updated row.

## 11. Backups and restore

- Logical (`pg_dump`) for small/portable; **physical base backups + WAL archiving** (pgBackRest, WAL-G, or the managed service's PITR) for point-in-time recovery; define RPO/RTO.
- Backups are encrypted, stored off the DB host, retained by policy, and **restore is tested on a schedule**; health reports last-backup age and WAL-archive lag.

## 12. Testing

- Test on the real engine and major version (not SQLite): collations, partial indexes, RLS, generated columns, locking and JSON behave as in production.
- Cover: unique/FK/check violation mapping, partial-unique semantics, RLS isolation (with and without the tenant setting), serialization/deadlock retry path, keyset pagination stability, UTC handling, migration `lock_timeout` behaviour, and up/down on a realistic fixture.

## 13. Pitfalls checklist

- [ ] All timestamps are `timestamptz`; session zone UTC.
- [ ] Every FK has an index.
- [ ] No `NOT IN (subquery)` on nullable columns.
- [ ] `lock_timeout` set in migrations; indexes `CONCURRENTLY`.
- [ ] Idle-in-transaction and statement timeouts configured.
- [ ] App role is not owner/superuser and has no `BYPASSRLS`.
- [ ] No session state assumptions behind a transaction pooler.
- [ ] Autovacuum enabled and monitored.
